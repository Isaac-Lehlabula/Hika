# Hiking Spot mobile app (Flutter)

The primary customer-facing product — Android + iOS from one codebase. See [`/docs/mobile-architecture.md`](../../docs/mobile-architecture.md) for the full design rationale (Riverpod choice, feature-based structure, design system, token storage).

## Structure

```
lib/
  core/           App-wide infrastructure: theme, networking (Dio + auth interceptor),
                  secure token storage, go_router config, environment config
  shared/         Reusable widgets (HikaButton, HikaTextField, HikaCard, HikaEmptyState)
  features/
    auth/           Register, login, email/phone verification, password reset
    profile/        Own profile view/edit
    drivers/        Become-a-driver flow, vehicle management, photo/document upload
    home/           The flagship "Where are you going home to?" search screen
    shell/          Bottom-nav shell, splash screen
test/             Mirrors lib/ structure
```

## Running locally

1. Start the backend: from the repo root, `docker compose up -d postgres mailhog`, then `dotnet run --project backend/src/Hika.Api` (see [`/backend/README.md`](../../backend/README.md)).
2. From this directory: `flutter pub get`
3. Run on a device/emulator/simulator: `flutter run`
   - Android emulator and iOS simulator both resolve the API's local address automatically (`AppConfig` in `lib/core/config/app_config.dart` handles the Android-emulator-vs-`10.0.2.2` quirk).
   - Override the API base URL for a physical device or staging: `flutter run --dart-define=API_BASE_URL=http://<your-machine-ip>:5080`
   - `flutter run -d chrome` also works for quick UI iteration in a browser — useful for fast feedback, but the shipped product targets Android/iOS, not web.

## Push notifications

A real Firebase project (`hiking-spot-f7640`) is configured — `lib/firebase_options.dart` was generated by `flutterfire configure`, which also wired `android/app/build.gradle.kts`/`android/settings.gradle.kts` for the Google Services Gradle plugin and added `android/app/google-services.json` (a client-side config file, safe to commit — it's the same values already in `firebase_options.dart`'s `android` block, not a secret). `PushService` (see `lib/core/push/push_service.dart`) registers the device's FCM token on login and deep-links a notification tap to the relevant screen.

Still outstanding before push actually reaches a device:

- **Backend credential** — the Firebase Admin service-account key is stored in that project's `dotnet user-secrets` locally (`Firebase:ServiceAccountJson`), never committed. For any other environment (a teammate's machine, Render), generate a fresh key (Firebase console → Project Settings → Service Accounts → Generate new private key) and set it there the same way — either `dotnet user-secrets set` locally, or as an env var (`Firebase__ServiceAccountJson`, double underscore) in production. Never put it in `appsettings.json` — that file is committed to git.
- **iOS APNs** — needs an active Apple Developer Program membership: enable the "Push Notifications" capability in Xcode (`ios/Runner.xcworkspace`), generate an APNs Auth Key in the Apple Developer portal, and upload it in Firebase console → Project Settings → Cloud Messaging → Apple app configuration. Android needs none of this — FCM talks to it directly.

If this project's Firebase config ever needs regenerating (e.g. a new environment, a renamed package), rerun `flutterfire configure` from this directory — it overwrites `firebase_options.dart` and the Android Gradle wiring together, so they don't need to be kept in sync by hand.
