# Implementation Roadmap

The primary product is the **Flutter mobile app**; the Next.js admin portal is secondary and deferred. From Phase 2 onward, each feature phase is built **vertically** — backend endpoints and the corresponding mobile screens land together, so the product stays usable (in the app) throughout development, not "backend-complete, then months of frontend work."

Each phase: explain → implement (backend + mobile together, from Phase 2 on) → automated tests (backend: xUnit; mobile: widget/unit tests as the app grows) → build/run → fix → update docs.

## What's runnable today

- Backend: `docker compose up -d postgres mailhog`, then `dotnet run --project backend/src/Hika.Api` — auth (register → verify email → verify phone OTP → login → refresh → profile edit → logout), driver profile/vehicle/photo/verification-submission flows, trip posting (locations, ordered stops, per-adjacent-stop-pair segment inventory, get/list/cancel), search (`GET /api/v1/search/trips` matching a rider's from/to against any sub-leg of a trip's stops; location autocomplete; live popular-routes aggregation), bookings (`POST /api/v1/bookings` reserves seats on a specific boarding→alighting range with a Postgres-advisory-lock-guarded transaction so two riders can never win the same last seat, plus accept/decline/cancel/complete and the driver's incoming-requests view), payments (accepting a booking captures a `Payment` via `IPaymentGateway` — `MockPaymentGateway` MVP implementation, auto-succeeds — split into platform fee and driver payout; `GET /bookings/{id}/payment` for status/receipt; `POST /bookings/{id}/refund`, driver-initiated for MVP), reviews (`POST /api/v1/reviews/bookings/{id}` — only once `Booking.Status == Completed`, direction inferred from the caller's role in the booking, one per person per booking; `GET /api/v1/reviews/users/{id}` paginated; `UserProfile.AverageRating`/`CompletedTripCount` recomputed on submission), and notifications/ride alerts (`INotificationDispatcher` persists an in-app `Notification` row — the inbox is just "my Notification rows" — fired on booking requested/accepted/declined, payment succeeded, and new review; `GET /api/v1/notifications/me` paginated, `POST /api/v1/notifications/me/{id}/read`; `POST /api/v1/ride-alerts` matches the same way search matches a trip's stops, firing a `RideAlertMatched` notification and marking the alert Fulfilled the moment a driver posts a matching trip) all work end-to-end against a real Postgres database. 203 automated tests passing (126 unit, 77 integration against a real Postgres via Testcontainers).
- Mobile: `flutter run` (see `mobile/hika_app/README.md`) — auth screens, "Become a driver" (license details, license photo submission), vehicle management (add/view/delete, photo upload with a primary-photo picker, registration-document submission), trip posting (a guided 4-step "post a trip" flow — vehicle, route, details, review — plus a trip-detail screen with cancel), search (the home screen's From/To fields open a location-autocomplete picker, Date/Passengers pickers, "Find a Hike" navigates to a sorted/filterable trip-card results list, and "Popular this month" is wired to real aggregated trip data instead of a hardcoded list), bookings (a reserve-seat screen on any non-owned scheduled trip — pick boarding/alighting stops and a seat count bounded by the real per-leg availability, submit a request — a Bookings tab listing the passenger's own requests/confirmations with a detail screen and cancel, and the driver's incoming-requests screen with accept/decline), payments (a receipt card — fare, platform fee, driver payout, provider reference — appears on a booking's detail screen once it's no longer Pending; the driver can refund a Confirmed booking from the incoming-requests screen), reviews (a star-rating + comment sheet on a Completed booking, direction-aware for both passenger and driver; the profile screen's rating row is now tappable through to a paginated reviews-received screen), and notifications/ride alerts (the Inbox tab is now a real paginated notification list — tapping an item marks it read and deep-links to the relevant booking/trip/reviews screen based on its type; ride alerts get their own screen reachable from the Inbox app bar, a creation sheet reused from both that screen and a no-results search's "Notify me" action) are all wired to the real backend and verified end-to-end. Bottom-nav shell in place with all five tabs now real. 42 automated widget/unit tests passing.

## Next up

**Phase 10 — Trust & safety**: backend reports/blocks/emergency contacts; mobile report/block UI and emergency-contact management.

Real FCM push delivery is **not** built — the backend's `Notification.Channel` enum already documents Push as designed-for-but-undelivered (no Firebase project exists in this environment); the in-app inbox is the actually-delivered channel, consistent with that decision.

`Payout` (many payments rolling into one driver payout run) is deliberately **not yet built** — see `domain-model.md` §6: it needs an actual payout-triggering mechanism (a scheduled job or the admin portal, Phase 11) that doesn't exist yet, so building the entity now would be speculative. Similarly, cancelling a trip does **not** yet cascade to declining/refunding its bookings — see the comment in `TripService.CancelAsync`; that's tracked for Phase 10 (Trust & Safety) since the policy questions it raises belong there.
