# Implementation Roadmap

The primary product is the **Flutter mobile app**; the Next.js admin portal is secondary and deferred. From Phase 2 onward, each feature phase is built **vertically** — backend endpoints and the corresponding mobile screens land together, so the product stays usable (in the app) throughout development, not "backend-complete, then months of frontend work."

Each phase: explain → implement (backend + mobile together, from Phase 2 on) → automated tests (backend: xUnit; mobile: widget/unit tests as the app grows) → build/run → fix → update docs.

## What's runnable today

- Backend: `docker compose up -d postgres mailhog`, then `dotnet run --project backend/src/Hika.Api` — auth (register → verify email → verify phone OTP → login → refresh → profile edit → logout), driver profile/vehicle/photo/verification-submission flows, trip posting (locations, ordered stops, per-adjacent-stop-pair segment inventory, get/list/cancel), search (`GET /api/v1/search/trips` matching a rider's from/to against any sub-leg of a trip's stops; location autocomplete; live popular-routes aggregation), bookings (`POST /api/v1/bookings` reserves seats on a specific boarding→alighting range with a Postgres-advisory-lock-guarded transaction so two riders can never win the same last seat, plus accept/decline/cancel/complete and the driver's incoming-requests view), payments (a driver accepting a booking request moves it to `AwaitingPayment` and initiates a `Payment` via `IPaymentGateway` — `OzowPaymentGateway`, a real South African instant-EFT redirect-based gateway, is used whenever `Ozow:SiteCode` is configured, falling back to the synchronous `MockPaymentGateway` otherwise; Ozow's outcome resolves asynchronously via a hash-verified webhook, `POST /api/v1/webhooks/ozow/{payment,refund}-notify`, moving the booking to `Confirmed`/`Declined` — split into platform fee and driver payout; `GET /bookings/{id}/payment` for status/receipt/redirect URL; `POST /bookings/{id}/refund`, driver-initiated for MVP; `GET /payment-return/{success,cancel,error}` are the unauthenticated pages Ozow's hosted checkout redirects back to), reviews (`POST /api/v1/reviews/bookings/{id}` — only once `Booking.Status == Completed`, direction inferred from the caller's role in the booking, one per person per booking; `GET /api/v1/reviews/users/{id}` paginated; `UserProfile.AverageRating`/`CompletedTripCount` recomputed on submission), notifications/ride alerts (`INotificationDispatcher` persists an in-app `Notification` row — the inbox is just "my Notification rows" — fired on booking requested/accepted/declined, payment succeeded, and new review; `GET /api/v1/notifications/me` paginated, `POST /api/v1/notifications/me/{id}/read`; `POST /api/v1/ride-alerts` matches the same way search matches a trip's stops, firing a `RideAlertMatched` notification and marking the alert Fulfilled the moment a driver posts a matching trip), trust & safety (`POST /api/v1/trust-safety/reports` about a user or trip; `POST/DELETE /api/v1/trust-safety/blocks/{userId}` plus `GET /blocks` for the blocker's own list — a block stops either party booking the other's trips, checked in `BookingService.RequestAsync`; `GET/POST/PUT/DELETE /api/v1/users/me/emergency-contacts`), and the admin surface (`/api/v1/admin/...`, gated by a DB-checked `Admin` authorization policy — `UserProfile.IsAdmin`, promoted only out-of-band via `Admin:BootstrapEmail` or direct DB access, never a self-service endpoint) covering user management (list/search, suspend/unsuspend), the verification review queue (approve/reject a driver-license or vehicle-registration submission, syncing `DriverProfile.IsVerifiedDriver`/`Vehicle.IsVerified`), trip oversight (list, remove/cancel), booking and payment oversight (list, admin-initiated refund via a new `IPaymentService.AdminRefundAsync`), safety-report resolution (resolve/dismiss), review moderation (delete, reversing the reviewee's cached rating aggregate via the new `UserProfile.RemoveCompletedTripReview`), a platform-fee setting (`GET/PUT /admin/platform-fees` — `Payment.Charge` now takes the fee rate as a parameter instead of a hardcoded constant, read from this admin-configurable `PlatformFeeSettings` singleton row), an analytics overview (user/trip/booking counts, GMV, platform fees, 30-day activity), and an append-only audit log (`GET /admin/audit-logs`) that every mutating admin action above writes to — all work end-to-end against a real Postgres database. 299 automated tests passing (193 unit, 106 integration against a real Postgres via Testcontainers).
- Mobile: `flutter run` (see `mobile/hika_app/README.md`) — auth screens, "Become a driver" (license details, license photo submission), vehicle management (add/view/delete, photo upload with a primary-photo picker, registration-document submission), trip posting (a guided 4-step "post a trip" flow — vehicle, route, details, review — plus a trip-detail screen with cancel), search (the home screen's From/To fields open a location-autocomplete picker, Date/Passengers pickers, "Find a Hike" navigates to a sorted/filterable trip-card results list, and "Popular this month" is wired to real aggregated trip data instead of a hardcoded list), bookings (a reserve-seat screen on any non-owned scheduled trip — pick boarding/alighting stops and a seat count bounded by the real per-leg availability, submit a request — a Bookings tab listing the passenger's own requests/confirmations with a detail screen and cancel, and the driver's incoming-requests screen with accept/decline), payments (a booking's detail screen shows an `AwaitingPayment` prompt with a "Pay now" button once the driver accepts, opening Ozow's hosted checkout in an external browser via `url_launcher`; a receipt card — fare, platform fee, driver payout, provider reference — appears once payment is no longer Pending; the screen refreshes both the booking and payment automatically when the app resumes from background, so the outcome shows up as soon as the passenger returns from paying, no manual pull-to-refresh needed; the driver can refund a Confirmed booking from the incoming-requests screen), reviews (a star-rating + comment sheet on a Completed booking, direction-aware for both passenger and driver; the profile screen's rating row is now tappable through to a paginated reviews-received screen), notifications/ride alerts (the Inbox tab is now a real paginated notification list — tapping an item marks it read and deep-links to the relevant booking/trip/reviews screen based on its type; ride alerts get their own screen reachable from the Inbox app bar, a creation sheet reused from both that screen and a no-results search's "Notify me" action), and trust & safety (a report sheet reused from both the trip-detail screen's AppBar menu — non-owner viewers can report/block the driver — and the driver's incoming-requests screen — a per-request menu to report/block a passenger; a Blocked users screen and an Emergency contacts screen, both reachable from a new Safety card on the profile screen) are all wired to the real backend and verified end-to-end. Bottom-nav shell in place with all five tabs now real. 65 automated widget/unit tests passing.

- Admin portal: `npm run dev` in `admin/` (Next.js 16, App Router) against `API_BASE_URL` (see `admin/.env.example`) — staff sign in at `/login` (a normal Hika account promoted via `Admin:BootstrapEmail`, never a self-service flow), gated by a layout-level check that calls a real admin endpoint and distinguishes "not logged in" (→ redirect to `/login`) from "logged in but not staff" (→ an inline "Not authorized" screen, since those are different problems). Every admin capability from the backend list above gets a page: Users (search, suspend/unsuspend with a reason), Verifications (approve/reject with a reason, filterable by status), Trips (remove with a reason), Bookings (read-only), Payments (refund with a reason), Reports (resolve/dismiss), Reviews (delete), Platform fee (view/update), Analytics (the dashboard's stat tiles), Audit log. Reason-collecting and confirmation actions use an in-page `<dialog>` component rather than `window.prompt`/`confirm` — both cleaner UX and, incidentally, necessary, since this sandboxed preview environment doesn't support native blocking dialogs at all. All Server Actions re-derive the caller's identity from an httpOnly session cookie set at login (never trust client-supplied identity), and `proxy.ts` (Next 16's renamed `middleware.ts`) silently refreshes an expired access token using the refresh-token cookie before a protected page renders, since Server Components can't set cookies themselves. Verified end-to-end against the live backend, including the suspend/unsuspend round-trip, a report resolution, a platform-fee change that measurably altered the next payment's fee split, a review deletion that correctly reversed the reviewee's cached rating, and the "logged in but not authorized" path for a non-admin account.

- Production hardening: `.github/workflows/{backend,mobile,admin}.yml` build/test all three apps on push/PR (path-filtered per app); `.github/dependabot.yml` runs weekly grouped dependency-update PRs for NuGet/npm/pub/GitHub Actions — both dormant until the repo is pushed to a GitHub remote, since neither exists locally. Rate limiting (`Microsoft.AspNetCore.RateLimiting`, config-driven via `RateLimiting:*`) is applied to the auth endpoints called out in `security.md` (login, OTP request/verify, password-reset request/confirm — partitioned per IP) and the report/block endpoints (partitioned per user); a dedicated integration test class exercises the real 429 behavior with a small configured limit, while every other integration test overrides the limit to effectively-unlimited so 97 unrelated tests didn't have to change. Added three load-relevant indexes found by auditing every admin list query against its EF configuration: `Booking(Status, RequestedAtUtc)`, `Payment(Status, CreatedAtUtc)`, `Review(CreatedAtUtc)` — mirroring the `Trip(Status, DepartureAtUtc)` index already in place from Phase 4.

## Next up

**Phase 12 remainder — blocked on external credentials, not on more engineering**: app-store release prep (Apple/Google developer accounts, signing certificates, store listing copy/screenshots) and swapping the mock SMS/identity-verification providers for real ones (an SMS provider, a document-verification provider — see `south-africa.md` for candidates) both need accounts and API keys this environment doesn't have. The payment provider is no longer on this list — Ozow is implemented end-to-end (see the Ozow row in the phase table above) — but it still needs a real merchant SiteCode/PrivateKey/ApiKey plugged into config, and its field-order/refund-endpoint assumptions verified against a live account, before it can actually move money (see `south-africa.md`). Everything else in Phase 12 that didn't need external credentials — CI, rate limiting, dependency scanning, load indexes — is done.

Search-result filtering for blocked users is **not** built — hiding a blocked user's trips from search needs the search endpoint (currently `[AllowAnonymous]`) to know the caller's identity when present, which is a bigger change than this phase's scope; the higher-value half (blocked parties can't book each other) is done. Cancelling a trip still doesn't cascade to declining/refunding its bookings either — see the comment in `TripService.CancelAsync` — the policy questions that raises (does the driver owe a refund? partial vs. full?) are better suited to product/business input than an engineering default, so it stays a tracked gap rather than a guessed-at implementation.

Real FCM push delivery is **not** built — the backend's `Notification.Channel` enum already documents Push as designed-for-but-undelivered (no Firebase project exists in this environment); the in-app inbox is the actually-delivered channel, consistent with that decision.

`Payout` (many payments rolling into one driver payout run) is deliberately **not yet built** — see `domain-model.md` §6: the admin portal exists now, but no payout-*triggering* mechanism (a scheduled job or an admin "run payout" action) does, so building the entity now would still be speculative.
